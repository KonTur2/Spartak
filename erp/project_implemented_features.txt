Актуальная сводка реализованного в проекте ERP Spartak
======================================================

Дата актуализации: 2026-04-13

1. Общая архитектура
- Проект реализован на Django и разделен на приложения `accounts`, `erp_app` и `fleet`.
- Корневые маршруты подключают авторизацию, общие ERP-разделы и отдельный модуль управления флотом.
- Базовый интерфейс построен на шаблонах Django с общей навигацией и ролевым доступом.

2. Авторизация и роли пользователей
- Реализованы регистрация, вход, выход и страница профиля пользователя.
- При регистрации пользователь выбирает роль, которая сохраняется через модель `UserRole`.
- Для новых пользователей автоматически создается профиль роли через сигналы Django.
- После входа пользователь перенаправляется в раздел, соответствующий его роли.
- В проекте используются роли: `director`, `accountant`, `logistician`, `crew`, `captain`, `fleet_manager`, `dispatcher`, `engineer`.
- Для ограничения доступа применяется декоратор `role_required`.
- Для капитанов настроен отдельный входной сценарий: после логина они попадают в собственный раздел технических сообщений по закрепленному судну.

3. Общие ERP-разделы
- Реализован директорский dashboard с демонстрационной статистикой, графиками, заказами и задачами.
- Подготовлены отдельные страницы разделов: финансы, логистика, флот, добыча, переработка, сбыт, документы, судоремонт.
- Переход в раздел "Флот" ведет в полноценный модуль `fleet`.
- Переход в раздел "Судоремонт" ведет в раздел ремонтов флота.

4. Модуль флота: сущности и данные
- Реализованы модели `Ship`, `CrewMember`, `ShipCrewRequirement`, `Voyage`, `Maintenance`, `Contractor`, `Notification`, `MaintenanceLog`, `RepairWork`.
- Для судна хранятся тип, IMO, статус, местоположение, техническое состояние, `engine_hours` и `last_repair_date`.
- Для экипажа хранятся пользователь, должность, закрепленное судно, дата окончания контракта и примечания.
- Для требований к составу экипажа задаются обязательные роли и количество по типу судна.
- Для рейсов хранятся судно, экипаж, даты, район промысла, план и факт улова, описание и признак завершения.
- Для ремонтов хранятся тип ремонта, даты, стоимость, статус, подрядчик, текстовый подрядчик, документы и набор выбранных работ `repair_works`.
- Для уведомлений хранятся тип сущности, код проблемы, severity, текст, статус прочтения и статус решения.
- Для капитанских сообщений хранится журнал `MaintenanceLog`: судно, дата и время записи, наработка на момент записи, текст заметки и автор записи.
- Для типовых ремонтных работ хранится справочник `RepairWork` с кодом, названием и базовой стоимостью.

5. Работа с судами
- Реализованы просмотр карточки судна, создание и редактирование судов.
- Проверяется обязательность имени и IMO, а также уникальность номера IMO.
- Для судна отображаются экипаж, история рейсов и история ремонтов.
- Фактический статус судна вычисляется не только из поля модели, но и из текущих рейсов и ремонтов через сервисный слой.

6. Работа с экипажем
- Реализован список экипажа с доступом для разрешенных ролей.
- Реализовано создание члена экипажа через интерфейс.
- При создании члена экипажа автоматически создается связанный пользователь и назначается роль `crew` или `captain` в зависимости от должности.
- Для экипажа рассчитывается состояние контракта: активен, скоро истекает, истек, без даты контракта.
- Реализована посадочная ведомость экипажа по всем судам или по выбранному судну.
- Реализован кадровый резерв экипажа: сотрудники могут существовать без привязки к судну и затем назначаться через интерфейс.
- Реализована отдельная страница назначения/изменения состава экипажа на конкретное судно.
- Для типов судов `fishing`, `transport` и `passenger` поддерживаются и автоматически создаются требования к минимальному составу экипажа.
- Для одного судна запрещается одновременное назначение двух капитанов; роли пользователей синхронизируются с должностью в экипаже.

7. Работа с рейсами
- Реализованы создание, редактирование и завершение рейса.
- Рейс можно создавать как из общего раздела, так и из карточки конкретного судна.
- В форме рейса доступен выбор судна, дат, района промысла, планового улова и нескольких членов экипажа.
- При сохранении выполняется валидация пересечения рейсов одного судна.
- Дополнительно проверяется пересечение рейса с ремонтами судна.
- Реализована проверка конфликтов по экипажу: один и тот же член экипажа не должен пересекаться по активным рейсам.
- Реализована бизнес-проверка контрактов экипажа на период рейса.
- При завершении рейса сохраняются фактический улов и дата завершения.
- Статус судна автоматически синхронизируется с состоянием рейса: судно уходит в море при активном рейсе и возвращается в порт после завершения, если нет других активных событий.

8. Работа с ремонтами и ТО
- Реализованы список ремонтов, просмотр карточки ремонта, создание, редактирование и завершение ремонта.
- Ремонт можно создавать как из общего раздела, так и из карточки судна.
- Проверяются пересечения ремонтов между собой.
- Проверяются пересечения ремонта с рейсами судна.
- Для аварийного ремонта предусмотрено отдельное поведение: конфликт с рейсом не блокирует сценарий полностью как для обычного ремонта.
- Статус судна автоматически переводится в состояние ремонта при активном ремонте.
- После завершения ремонта статус судна возвращается в море или в порт в зависимости от других активных событий.
- Реализован учет подрядчиков с отдельным CRUD: список, создание, редактирование и удаление.
- Для всех судов поддерживается плановый ремонт по `last_repair_date` с единой периодичностью; при создании нового судна плановый ремонт может быть запланирован автоматически.
- Реализован расчет даты следующего планового ремонта и отображение планового статуса в карточке судна.
- Один ремонт может включать несколько типовых работ из справочника `RepairWork`.
- Стоимость ремонта рассчитывается как сумма базовых стоимостей выбранных работ и сохраняется в `Maintenance.cost`.

9. Готовность судна и сервисная бизнес-логика
- Вынесен сервисный слой `fleet/services.py` для вычисления операционного состояния судов.
- Реализована проверка готовности судна к эксплуатации через `ship_readiness_service`.
- Учитываются минимальные обязательные роли, а также настраиваемые требования `ShipCrewRequirement` по типу судна.
- Сервис различает блокирующие проблемы, предупреждения и информационные сообщения.
- Учитываются истекшие контракты, скоро истекающие контракты и отсутствие даты контракта.
- Реализовано вычисление "здоровья" рейсов и ремонтов: просрочка старта, слишком длинный рейс, затянувшийся ремонт и другие канонические состояния.
- Реализовано агрегирование системных проблем по судам, рейсам, ремонтам и экипажу.

10. Dashboard флота и аналитика
- Главный dashboard флота показывает список судов, их фактические статусы и показатели готовности.
- На dashboard есть фильтрация судов по готовности и состоянию укомплектованности экипажа.
- Реализована сортировка судов по имени и критичности.
- Для активных рейсов реализованы фильтры по состоянию и сортировка по дате, имени судна и критичности.
- На dashboard выводятся последние ремонты и агрегированная проблематика по системе.
- Реализован отдельный отчет "Состояние флота" (`fleet_health_report`) с KPI по готовности, экипажу, статусам судов, проблемным рейсам и ремонтам.
- Реализован отчет по ремонтам и графику ТО (`maintenance_report`) с фильтрацией по периоду и статусу.
- Реализован отчет по наработке флота (`performance_report`) по завершенным рейсам за период.

11. Уведомления и контроль проблем
- Реализована модель уведомлений по проблемным объектам системы.
- Реализован список уведомлений с фильтрами по активности, решенности, непрочитанности и severity.
- Реализована детальная страница уведомления.
- Сервис `sync_notifications_from_problem_states` создает уведомления на основе найденных системных проблем.
- Повторный запуск синхронизации не создает дубликаты.
- При исчезновении проблемы уведомление помечается как решенное, а при повторном появлении может реактивироваться.
- Новое сообщение капитана создает отдельное уведомление для инженерно-диспетчерских ролей.
- При сообщениях капитана по ключевым словам система может автоматически создать техпредупреждение и внеплановый аварийный ремонт без дублирования активных записей.
- В боковом меню отображается счетчик непрочитанных уведомлений по модулю флота.
- При открытии карточки уведомления оно автоматически помечается как прочитанное.

12. Маршруты и пользовательские сценарии
- Для модуля флота опубликованы маршруты dashboard, судов, рейсов, экипажа, ремонтов, подрядчиков, отчетов и уведомлений.
- Для ролей `director`, `fleet_manager`, `dispatcher`, `engineer`, `crew`, `captain` настроены разные уровни доступа к операциям.
- Диспетчер имеет доступ к ключевым операциям по рейсам и части отчетности.
- Инженер подключен к просмотру и отчетности по техническому состоянию и уведомлениям, а также к редактированию и завершению заявок на ремонт.
- Для капитана реализован отдельный интерфейс `captain_panel`: он видит только свое судно, историю собственных технических сообщений и форму отправки сообщения для диспетчера/инженера.
- Для директора, инженера, диспетчера и fleet manager реализована отдельная единая лента сообщений капитанов.

13. Тесты и подтвержденное поведение
- В `fleet/tests.py` присутствует крупный набор автоматических тестов.
- Тестами покрыты вычисление фактического статуса судна, проверка готовности, требования к экипажу и валидация контрактов.
- Проверены сценарии создания и редактирования рейсов, завершения рейса и реакции на некорректные данные.
- Проверены сбор проблемных состояний системы и их канонические коды.
- Проверены создание, обновление, разрешение и реактивация уведомлений.
- Проверено наполнение контекста dashboard и корректная агрегация проблем.
- Добавлены smoke-тесты на сквозной сценарий: капитан сообщает о проблеме, инженер видит сообщение и работает с ремонтом, директор видит итоговый результат.
- Проверены ограничения капитанского доступа только к своему судну и запрет второго капитана на одном судне.
- Проверены автоматические уведомления по новым сообщениям капитанов и пометка уведомления как прочитанного при открытии.

14. Вспомогательные материалы и скрипты
- В проекте есть скрипты для создания пользователей и тестовых данных флота.
- В репозитории присутствуют дополнительные текстовые отчеты и технические заметки по отдельным частям проекта.

15. Итоговое состояние
- Наиболее развитой частью проекта является модуль управления флотом.
- В проекте уже реализованы не только интерфейсы, но и значимая бизнес-логика: готовность судна, валидация экипажа, контроль пересечений, капитанские сообщения, плановые и аварийные ремонты, отчеты и уведомления.
- Общие ERP-разделы вне флота в основном представлены страницами и навигацией, тогда как флот содержит полноценные CRUD-сценарии и сервисную логику.
